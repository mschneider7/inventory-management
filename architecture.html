Data flow

  1. User changes a filter Time Period, Warehouse, Category, or Order Status. State lives in module-level refs in useFilters.js, shared by every view.
  2. View requests data through the API client getCurrentFilters() builds the filter object; api.js drops values equal to all and sends the rest as query params.
  3. FastAPI route receives the request Endpoints such as /api/orders and /api/dashboard/summary accept warehouse, category, status, and month.
  4. Filtering runs in memory apply_filters and filter_by_month operate on lists loaded from JSON at startup.
  5. Pydantic validates the response response_model enforces the shape (InventoryItem, Order, DemandForecast, BacklogItem).
  6. View stores raw data and derives the rest Raw results go into refs such as allOrders and inventoryItems; totals and chart series are computed properties.

Things worth knowing

State is not persistent

Data is loaded once when the server starts. Restarting resets everything, and any edit to the JSON files needs a restart to appear.

Inventory has no time dimension

The month filter applies to orders and the dashboard summary, not to inventory.

Frontend and backend are out of sync. api.js defines calls to /tasks and /purchase-orders (create, delete, toggle, lookup by backlog item), but main.py has no routes for them. It only has read-only GET endpoints plus a CreatePurchaseOrderRequest model that no route uses. Those features will fail against the current backend.
